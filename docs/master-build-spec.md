# Shodh Master Build Specification

This document is the consolidated implementation brief for the complete Shodh system. It supersedes the original nine prompts where a later requirement requires an earlier architectural change.

## 1. Foundation and infrastructure

Create a monorepo containing `backend`, `frontend`, `evaluation`, `docs`, CI, and deployment configuration. Backend uses Python 3.11 + FastAPI + Poetry. Frontend uses Next.js 15 + React 19 + Tailwind with shadcn-style primitives. Infrastructure uses Qdrant, PostgreSQL, Redis, FastAPI, a separate Celery worker, and Next.js, all on a shared `shodh` network with health checks.

The API exposes `GET /health`. The frontend has a restrained research-workspace landing page rather than a generic AI marketing template. `docker compose up --build` is the canonical local startup path.

## 2. Document ingestion

`POST /ingest` accepts a PDF, persists it to the shared upload volume, creates a stable job ID, and returns immediately. Celery processes the job asynchronously through Redis.

The worker:

1. extracts text page-by-page with PyMuPDF;
2. recursively chunks each page with a 512-token target and 128-token overlap;
3. never crosses page boundaries;
4. embeds chunks with Cohere `embed-multilingual-v3.0` in batches of 96;
5. creates named dense and BM25 sparse vectors in Qdrant;
6. stores payload `{page, doc_id, chunk_id, text, language}`;
7. records document metadata in PostgreSQL;
8. exposes `GET /ingest/{job_id}` for polling.

Document state is `queued`, `processing`, `complete`, or `failed`.

## 3. Core RAG query pipeline

`POST /query` accepts a question, document ID, and optional language filter.

The pipeline detects the question language, creates a Cohere multilingual query embedding, retrieves dense top-20 and BM25 top-20 candidates, normalizes each score family, and fuses them with configurable `alpha=0.7`.

The fused top-20 are reranked by local `cross-encoder/ms-marco-MiniLM-L-6-v2`. Four chunks become the generation context.

Gemini receives a grounding prompt requiring:

- answers only from supplied context;
- `[page X, chunk Y]` citations;
- explicit acknowledgement when the answer is absent;
- the same language as the user's question.

The response contains the answer, citations, model, latency, detected language, and retrieved context trace. The complete retrieval trace and final answer are persisted to `query_logs`.

## 4. Multilingual behavior

Language detection is performed at the start of the query pipeline. It is stored in query logs and returned in the API response. Qdrant payloads also contain chunk/document language, enabling an optional language filter without changing the underlying retrieval pipeline.

English and Hindi queries over the same corpus should retrieve relevant evidence and generate answers in the corresponding query language.

## 5. Evaluation

`evaluation/golden_dataset/questions.json` contains 15 editable starter examples using the required schema. `evaluation/run_eval.py` calls the live `/query` endpoint, collects the full retrieved contexts, and evaluates faithfulness, answer relevancy, context precision, and context recall with RAGAS.

Reports are emitted as JSON and HTML and grouped by language and document type where document-type metadata is available. The evaluator uses Gemini rather than introducing a hidden second provider.

The evaluation API is `POST /evaluate`.

## 6. Frontend product

The frontend contains:

- landing page;
- `/upload` with drag/drop, progress, and job polling;
- `/chat` with document selection, grounded answer cards, expandable citations, and query history;
- `/docs` with indexed documents and deletion;
- `/eval` with evaluation trigger, language metrics table, and Recharts visualization.

All API communication goes through `/lib/api.ts`. UI primitives follow shadcn conventions. Loading skeletons, error toasts, empty states, dark mode, and a local API-key gate are included.

Visual direction: mature research tool, not a template marketplace. Use typography, spacing, borders, information hierarchy, and evidence visibility as the primary design language. Avoid excessive gradients, glassmorphism, oversized hero copy, decorative blobs, and gratuitous animations.

## 7. Evaluation dashboard and product polish

The dashboard consumes the same evaluation report generated by the backend. Query history consumes `GET /query_logs`. Authentication is intentionally lightweight for the first production iteration and can later be replaced by a real identity provider without changing the application API.

## 8. Deployment and CI/CD

Alembic owns PostgreSQL schema migrations. Backend startup runs migrations before Uvicorn. Production compose settings use `restart: always`, bounded resources, and rotating JSON logs.

GitHub Actions gates deployment on Python tests and a Next.js production build, then publishes backend and frontend images to GHCR. A hosted-platform deploy hook can trigger Railway or Render after publication. Secrets remain in GitHub/hosting secret stores.

Required environment variables are documented in `.env.example`.

## 9. Documentation and research output

The repository includes:

The paper must never contain invented evaluation numbers. Results are generated from the actual golden dataset and current pipeline configuration.

## Cross-stage invariants

- `doc_id` is the stable identity of an ingested document.
- `chunk_id` is stable within a page, e.g. `p12-c3`.
- Qdrant payload is the source of truth for page/chunk evidence.
- PostgreSQL stores application metadata and query traces, not the document vectors.
- Provider integrations are isolated behind small service classes.
- The frontend does not implement retrieval logic.
- Evaluation consumes the same `/query` contract used by the product.
- Schema changes go through Alembic.
